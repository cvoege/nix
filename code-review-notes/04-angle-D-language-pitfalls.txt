2. WHAT I AM LOOKING FOR
================================================================================

Classic JS/TS footguns that this diff introduces or re-exposes, specifically:

(a) Stateful global RegExp: `/g` or `/y` regex literal held in a module-level
    const and used with `.test()` / `.exec()`. `lastIndex` survives across calls,
    so repeated calls on equivalent inputs alternate true/false. Also: does a
    polluted `lastIndex` leak into other consumers of the same regex object
    (`String.prototype.matchAll` reads `lastIndex` from the source regex when it
    clones it; `String.prototype.match` with /g resets it to 0 first).

(b) Falsy-zero / empty-string truthiness checks introduced by the JS->TS
    conversion (`if (x)` where x can be 0, '', or []).

(c) Boolean arithmetic rewrites (`+= cond` -> `+= cond ? 1 : 0`).

(d) Set semantics (copying a Set, deduping object references by identity).

(e) `Object.keys` / `Object.entries` on possibly-undefined values, and
    `Object.keys(arr).length` vs `arr.length` semantic drift.

(f) NaN propagation from `?? NaN` sentinels into geometry/comparison code.

(g) Async pitfalls: `await` in loop, missing await, floating promises,
    async/non-async signature flips, lazily-initialised caches shared by
    concurrent awaits.

(h) O(n^2) spread-in-reduce and accumulator/seed aliasing.

(i) Type lies: `as`, `as unknown as`, `!`, and `@ts-expect-error` used to
    silence a mismatch instead of fixing the root type — especially where the
    value genuinely CAN be undefined at runtime, or where the only caller is an
    untyped `.js` file so TS can never catch the lie.

(j) React: `@ts-expect-error` above a JSX attribute.

Repo rules that make some of these hard findings rather than nits
(/Users/colton/code/monorepo/CLAUDE.md):
  - "Fix the root type instead of casting. `as any` / `as unknown as X` is rarely
     the answer."
  - "Narrow with type guards, not `@ts-expect-error`, casts, or non-null
     assertions."
  - "Fix root causes ... Never patch the same value in more than one place."

CONCLUSION (CONFIRMED, two independent failure modes):
  (i) Alternation. `RegExp.prototype.test` on a /g regex starts at `lastIndex`
      and, on success, sets `lastIndex` to the end of the match; on failure it
      resets to 0. `String.prototype.match` with /g sets lastIndex = 0 FIRST,
      which is why the old code was immune. So in the
      buildAlephFormulasMap loop every second Aleph formula is classified as
      non-Aleph and dropped ("Ignoring non-Aleph formula").
  (ii) Cross-contamination into matchAll. Per spec, RegExp.prototype[@@matchAll]
      clones the regex and copies `lastIndex` from the source. So after a
      successful `.test()` leaves lastIndex = 24, `splitAlephFormula`'s
      `matchAll(ALEPH_FORMULA_REGEX)` starts scanning at offset 24 and finds
      nothing -> `{nFormulas: 0}` -> `parseAlephFormulaArraySize` returns null ->
      findArrayAlephFormulaInternal's cache-miss branch (L949-984) can never
      determine an array formula's output size.
